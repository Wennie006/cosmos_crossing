# 宇宙人歌词填字游戏 — 产品需求文档（PRD）

- 版本：v0.1（MVP）
- 日期：2026-09-01
- 状态：待评审
- 类型：非商业、个人粉丝向 H5 小项目

---

## 1. 背景与目标

### 1.1 背景
为台湾乐团「宇宙人」制作一个歌词填字游戏（crossword）网站，粉丝自娱，非商业。
第一版（MVP）只做「填字游戏」一个板块，跑通完整体验闭环。

### 1.2 MVP 目标
- 用户能在一个页面内完成一道歌词填字谜题（简体中文）。
- 全部填对后自动停表，弹出完成弹窗，展示用时并播放该曲 15 秒片段。
- 支持「再玩一次」随机进入另一关。
- 视觉简约，使用一张背景图做 `multiply` 正片叠底处理。
- 代码结构为后续「转微信小程序」和「云端排行榜」预留接口，本期不实现。

### 1.3 非目标（MVP 明确不做）
- 乐队介绍、歌曲列表、歌手资料等其他板块。
- 多关卡选择列表（关卡切换只通过「再玩一次」随机）。
- 账号 / 登录 / 后端服务。
- 云端排行榜的实际实现（仅预留客户端接口与数据契约）。
- 反馈音效（点击、填对提示音等）。仅保留「完成后播放歌曲片段」。
- 分享卡片（图片生成）。MVP 仅「复制链接 + 文案」。
- 歌词批量爬取（后续扩展关卡时再做，本期歌词由用户上传）。
- 逐格实时校验、错误高亮。

## 2. 名词定义

| 术语 | 含义 |
|---|---|
| 关卡 / 谜题（Puzzle） | 一道填字题。MVP 中一关的所有句子来自**同一首歌**。 |
| 词条（Entry） | 谜题中的一行歌词，横向（`direction: horizontal`）或纵向（`direction: vertical`）排布。 |
| 交叉格（Crossing） | 同时属于一个横向词条和一个纵向词条的格子，是词条互相约束的锚点。 |
| 空格（Blank cell） | 需要用户填写的格子。 |
| 预填格（Prefilled cell） | 谜题开局即给出正确字、不可编辑的格子（额外提示，每关 1–2 个）。 |
| 候选字盘（Tray） | 页面下方打乱排列的候选字，用户点选后填入选中的空格。 |
| 干扰字（Distractor） | 字盘中不属于任何答案的字，用于增加难度。 |

## 3. 用户与核心场景

- **用户**：宇宙人的听众 / 粉丝，移动端竖屏浏览为主。
- **核心流程**：
  1. 打开页面 → 随机载入一关（显示歌名作为关卡标题）。
  2. 观察网格结构，点空格选中 → 点字盘里的字填入。
  3. 卡住时点「提示」，自动补一个空。
  4. 全部填对 → 自动停表 → 完成弹窗（用时 + 片段播放 + 分享 + 再玩一次）。
  5. 点「再玩一次」→ 随机进入另一关，计时清零重来。

## 4. 功能需求

### 4.1 关卡与内容

- MVP 至少包含 **2 个关卡**（2 首歌），以支持「再玩一次」切换到不同的歌。建议 3 首（已有 3 首歌词）。
- 每个关卡数据独立，包含：`puzzleId`（整数编号）、歌手、歌词词条布局、预填格、干扰字池。15 秒片段为 MP3，命名 `{puzzleId}.mp3`。歌名仅用于内部标识与完成后展示。
- 首次进入随机选一关；「再玩一次」从「非当前关卡」中随机选一关。
- **不显示歌名、无逐句文字线索**（决策已定，原 §9-D1 关闭）。谜题为「粉丝凭歌词记忆 + 提示字 + 交叉约束还原」的识别/回忆类玩法。歌名在**完成弹窗**中揭晓。
- 谜题的布局与提示字生成规则见 `docs/puzzle-generation.md`。

### 4.2 填字网格

- 采用「方案 X」+ `docs/puzzle-generation.md` §0.2 的结构约束：恰有一条横向词条与所有纵向词条交叉，纵向词条之间不交叉，至多一条附加横向词条与某条纵向词条交叉；**词条行内几乎全部为空格**，仅交叉格和预填格提供已知信息。不显示任何逐句文字线索。
- 网格用 DOM（CSS Grid）渲染，非 canvas。
- 每格为正方形，居中显示单个汉字。
- 格子状态：
  - 空（未填）
  - 已填（用户填入，可修改）
  - 预填（灰底，不可编辑）
  - 选中（当前激活格，高亮边框）
  - 当前词条高亮（选中格所属整条 horizontal 或 vertical 词条的浅色底）
- 交叉格同时属于两个词条；点击交叉格在 horizontal / vertical 之间切换当前方向（标准填字交互）。
- 网格尺寸建议 **≤ 11 列**，保证 375px 宽竖屏下格子 tap 目标 ≥ 32px；最终行列数依歌词定稿确定。
- 网格宽度 = `min(100vw - 两侧留白, 最大宽度)`；格子边长 = 网格宽度 / 列数，用相对计算，不写死 px。

### 4.3 输入交互

- **选格**：点任意空格 → 该格选中；再点一次交叉格 → 切换方向。
- **填字**：选中格后，点字盘中的字 → 该字填入选中格 → 选中格自动前进到当前词条方向的下一个空格（跳过预填格和已填格）。
- **改字**：点已填格选中它，直接点字盘另一个字覆盖；被覆盖的原字**退回字盘**。
- **清除**：再次点击「已选中的已填格」→ 清空该格，字退回字盘。
- **字盘消耗**：填入一个字即从字盘移除一枚对应字；清除 / 覆盖 / 退格时该字返还字盘。
- 字盘中字全部用完但仍有空格 → 说明有放错，用户需自行调整（不做强校验提示）。

### 4.4 候选字盘（Tray）

- 组成 = 所有空格所需的正确字（**按空格逐一计数，重复字重复提供**）+ 干扰字。
- 干扰字数量 ≈ `ceil(0.3 × 正确字总数)`，取整；来源优先取该关卡歌曲的其它歌词字符，池不足时由作者在关卡数据里手动补充（`distractorPool`）。
- 字盘整体打乱排序，位于网格下方，可横向换行 + 纵向滚动，最大高度约 30vh。
- 每枚字 tap 目标 ≥ 40px。
- 字盘只反映「当前可用」的字（已填入网格的字不在字盘显示）。

### 4.5 提示功能

- 页面提供「提示」按钮。
- 点击一次 → 自动填入**网格阅读顺序（左上→右下）中的第一个空格**的正确答案，并从字盘移除一枚对应字（字盘中无对应字则直接填入）。
- **次数不限，不扣分、不加时、不打标记**（MVP 不记成绩）。
- 客户端**记录 `hintCount`**（提示使用次数），本期不展示，为后续排行榜 / 数据分析预留。
- 注意与「预填提示字」区分：预填是开局给定、每条词条 1–2 个（含交叉格，规则见 `docs/puzzle-generation.md` §6.3）；此处「提示」按钮是游戏中按需消耗的补空功能。

### 4.6 计时器

- 正计时，从 `00:00` 开始向上走，精确到**秒**，显示格式 `mm:ss`（超过 60 分钟显示 `h:mm:ss`）。
- **启动时机**：用户在本关的第一次有效操作（首次选格或首次填字）时启动。启动前恒显 `00:00`。
- **不暂停**：切后台 / 锁屏 / 弹窗均不停表（完成时才停）。
- 实现：`sessionStorage` 记录 `startEpoch`；显示用时 = `now - startEpoch`。刷新后从 `sessionStorage` 恢复 `startEpoch` 继续计时。
- 完成瞬间记录 `finishEpoch`，用时 = `finishEpoch - startEpoch`，停止刷新。

### 4.7 完成判定与完成弹窗

- **判定**：每次填字 / 清除后检查——所有空格均已填写 **且** 每个格子的字与答案一致。满足则判定完成。
- 完成时：
  1. 停表。
  2. 弹出**完成弹窗**（模态，遮罩背景）。
- **完成弹窗内容**：
  - 标题文案（如「完成！」）+ 用时 `mm:ss`。
  - 一句彩蛋文案（可与关卡 / 歌曲绑定，关卡数据里配 `successText`，可选）。
  - **歌曲片段播放（音频）**：加载该关 15s MP3（`assets/clips/{puzzleId}.mp3`）。
    - 进入弹窗尝试自动播放。
    - 自动播放被浏览器拦截时，显示一个「▶ 播放」按钮，用户点击后播放。
    - 带一个**小的「重播」控件**，用户可重复播放片段。
    - 无视频画面，播放期间背景图正常显示。
  - **「分享」按钮**：见 §4.9。
  - **「再玩一次」按钮**：见 §4.8。
- 弹窗可关闭；关闭后停留在已完成的网格（只读展示态），主操作引导为「再玩一次」。

### 4.8 再玩一次

- 完成弹窗内的「再玩一次」：
  - 从「非当前关卡」的关卡池中**随机**选一关。
  - 清空网格、字盘、计时（`startEpoch` 重置）、`hintCount`。
  - 关闭弹窗，进入新关卡的初始态（计时未启动）。
- MVP 仅 2 关时，效果为切换到另一关。

### 4.9 分享（MVP 最小实现）

- Web 环境无原生分享卡片能力，MVP 分享按钮点击后：
  - 复制到剪贴板：**站点链接 + 一句带用时的文案**（如「我用 03:42 完成了宇宙人《歌名》的歌词填字，你也来试试：<链接>」）。
  - 给出「已复制」轻提示。
- 分享卡片（图片生成 / 小程序 `onShareAppMessage`）**延后到接入微信小程序阶段**再做。
- 文案模板放在配置中，便于后续替换。

### 4.10 进度保留

- 使用 `sessionStorage` 固定一条进度记录（键 `cosmos:progress`），内含 `puzzleId`（整数）、每个空格已填的字、`startEpoch`、`hintCount`。
- **下拉刷新 / 页面 reload**：从 `sessionStorage` 读回，`puzzleId` 与谜题库匹配则恢复该谜题的进度与计时。
- **关闭标签页 / 退出浏览器后重新进入**：`sessionStorage` 已清空，按全新会话处理（随机新关卡，计时未启动）。
- **关卡选择与「再来一局」**：逻辑见 `docs/puzzle-generation.md` §11——首次进入从谜题库均匀随机选一关；「再来一局」从「`puzzleId` 不等于当前关」的谜题中均匀随机选一关，库中仅一关时重新加载当前关。
- 已知边界：部分浏览器、微信内置浏览器在下拉刷新时也可能清空 `sessionStorage`，此时按全新会话处理。MVP 不额外兜底。

### 4.11 背景与视觉

- 整体简约风格，浅色基调。
- 背景层结构（从下到上）：
  1. 纯色底（近白，建议 `#F7F5F1` 或 `#FFFFFF`，最终定稿时确认）。
  2. 用户提供的背景图，`mix-blend-mode: multiply`，必要时叠加低透明度，保证前景对比度。
  3. 内容层（网格 / 字盘 / 计时 / 按钮），网格格子为不透明白底 + 描边，保证可读。
- 背景图由用户提供（不再使用团员照片拼贴）。
- 已知风险：微信小程序对 `mix-blend-mode` 支持有限，转小程序阶段可能改为「预合成好的背景图」。H5 阶段不受影响。
- 竖屏设计，不做横屏适配（横屏可用即可，不专门优化）。

### 4.12 音频片段

- 每关一个 15 秒左右的 **MP3 音频**，文件由用户提供，命名 `{puzzleId}.mp3`（1.mp3 / 2.mp3 / 3.mp3），放在 `src/assets/clips/`。
- 仅在完成弹窗中播放，无视频画面。
- 自动播放策略见 §4.7；提供手动播放与小重播控件。
- MP3 建议：128–192 kbps，单个 ≤ 500 KB，便于移动端加载。

## 5. 数据结构设计

### 5.1 关卡数据（puzzle JSON）

- 每关一个 JSON 文件，位于 `src/puzzles/`。
- **权威 schema 与字段说明见 `docs/puzzle-generation.md` §10。** 要点：`puzzleId` 为整数编号，由知识库分配，决定文件名 / 片段名 / 加载顺序 / 再来一局选择；`entries[]`（`text` / `direction` ∈ {horizontal, vertical} / `row` / `col`）是唯一权威来源，`entries[0]` 为第一条词条；`prefilled[]` 为每条词条 1–2 个提示格；`song.clipSrc` / `clipDuration` 可省略；`traySeed` 用于确定性重建字盘；不显示歌名，`song.title` 仅内部标识与完成弹窗揭晓用。
- 谜题由 `docs/puzzle-generation.md` 描述的生成器产出草稿，作者可手改 `entries` / `prefilled` 后重跑校验。

### 5.2 规则与派生

- **交叉格**由构建时脚本自动推导：任一 horizontal 词条与 vertical 词条经过的同一格即交叉格，两者在该格的字必须一致（构建校验）。
- **空格集合** = 网格中被任意词条覆盖的格 − 预填格。
- **答案** = 每格由其所属词条推导出的唯一字。
- **字盘多重集** = 每个空格贡献一枚其答案字（重复字重复计）+ `ceil(distractorRatio × 空格数)` 枚干扰字，按 `traySeed` 确定性打乱。`distractorRatio` 默认 0.30。

### 5.3 构建时校验脚本（`scripts/validate-puzzles.ts`）

校验项与 `docs/puzzle-generation.md` §8.1 一致，含：所有词条落在网格内、`text` 长度等于占用格数、交叉格满足一致性约束、无同方向词条部分重叠、预填格落在某词条上、干扰字符来源足够、`puzzleId` 在谜题库内唯一。并输出 §8.2 的文本网格预览供人工核对。

### 5.4 排行榜预留接口（`src/services/leaderboard.ts`）

本期为**空实现 / 本地占位**，定义清楚契约：

```ts
interface ScoreSubmission {
  puzzleId: number;
  seconds: number;
  hintCount: number;
  clientTs: number;      // 客户端完成时间戳
}

interface LeaderboardEntry {
  rank: number;
  seconds: number;
  hintCount: number;
  nickname?: string;
}

// MVP：submitScore 仅写入 localStorage；getTop 返回本地或空数组
async function submitScore(s: ScoreSubmission): Promise<void>;
async function getTop(puzzleId: number, limit?: number): Promise<LeaderboardEntry[]>;
```

后续接入云函数 / 微信小程序云开发时，仅替换该模块实现，不动游戏逻辑。

## 6. 技术方案

### 6.1 技术栈

- **纯 Vite + Vue 3 + TypeScript**（不使用 uni-app）。首要目标是尽快跑通 MVP，走最直接的技术路径。
  - 本期：`vite build` 产出静态站点，部署到 GitHub Pages。
  - 微信小程序为后续目标，届时另用 1–2 天重写视图层（`src/core/` 逻辑层不动）。本期不做任何小程序兼容性处理。
- **`src/core/` 保持纯 TS、无框架依赖、可单测**（谜题模型、布局、字盘、计时、游戏逻辑），为将来转小程序做复用准备。Vue 组件只负责渲染与事件转发。
- 状态管理：Pinia。
- 不引入 UI 组件库，样式手写（简约风、体积可控）。
- 字体：系统字体回退栈，不打包字体文件。谜题内容定稿后再评估是否为「格子内汉字」引入轻量字体子集。

### 6.4 兼容性

- 目标：移动端主流浏览器（iOS Safari、Android Chrome、微信内置浏览器）近 2 年版本。
- `mix-blend-mode`、`sessionStorage`、`navigator.clipboard`（分享复制，降级到提示手动复制）、`<video>` 自动播放策略在真机验证。
- 本期不做微信小程序兼容性处理。

### 6.5 性能

- 首屏资源（不含 MP3）目标 < 500 KB gzip。
- MP3 懒加载：仅在完成弹窗打开时才请求。
- 网格与字盘渲染规模小（≤ 121 格 + 数十枚字），无性能压力。

## 8. 分步开发计划（每步交付、评审后继续）

> 遵循「每一步做完先给你看结果，不一次性做完」。

1. **步骤 0：脚手架**
   Vite + Vue3 + TS 初始化，单页面空壳，`npm run dev` 本地跑通、`npm run build` 产出 `dist/`。GitHub 仓库 + Pages Actions 配好，拿到公开链接。交付：可访问的空白页（本地 + 线上）+ 目录结构。
2. **步骤 1：关卡数据模型 + 生成器 + 校验脚本**
   按 `docs/puzzle-generation.md` 实现 `puzzleModel.ts`（解析 / 交叉推导 / 派生答案）、布局阶段生成器、`validate-puzzles.ts`（硬校验 + 文本预览）。用《一万小时》的 `curatedLines` 产出首关草稿。交付：文本预览 + puzzle JSON。
3. **步骤 2：静态网格渲染**
   `CrosswordGrid.vue` 渲染网格、预填格、空格，无交互。交付：真机截图。
4. **步骤 3：字盘 + 填字交互**
   `trayGenerator.ts` + `CandidateTray.vue` + `gameEngine.ts`：选格、填字、改字、清除、方向切换、字盘增减。交付：可玩（无完成判定）。
5. **步骤 4：计时器 + 完成判定 + 进度保留**
   `GameTimer.vue`、完成判定、`sessionStorage` 持久化与刷新恢复。交付：能填完触发「完成」态。
6. **步骤 5：提示功能**
   `HintButton.vue` + `hintCount`。交付：提示补空可用。
7. **步骤 6：完成弹窗 + 片段播放 + 分享 + 再玩一次**
   `CompletionDialog.vue`：用时、MP3 音频播放（自动 + 手动 + 小重播）、复制链接分享、随机再玩。交付：完整闭环（用占位 MP3）。
8. **步骤 7：视觉与背景**
   接入背景图 + `multiply` + 简约样式打磨，竖屏适配。交付：视觉稿级别真机效果。
9. **步骤 8：真实内容接入 + 联调**
   接入用户提供的 2–3 首歌 `curatedLines`、MP3，跑校验，真机全流程测试。交付：可上线 MVP。
10. **步骤 9：部署**
    GitHub 仓库 + Pages 部署，出正式链接。
